## Scope

How a villager decides to go shopping, finds a target, walks there, and every way that trip can end (`docs/spec/domains/customer.md`, `CUSTOMER-REQ-001..009`; `04-architecture.md` `ARCH-DEC-002`, `ARCH-DEC-005`; `decisions/DEC-009-chance-per-restock.md`). A mixin on `Villager.registerBrainGoals(Brain<Villager>)`, injected at `RETURN`, adding a `ShoppingTrip` behaviour as one candidate in `Activity.WORK`'s priority set via `Brain.addActivity(...)` (`CUSTOMER-REQ-001`) — first step: read vanilla's `WORK` activity package (`VillagerGoalPackages.getWorkPackage`) to pick a priority slot that does not collide with an existing vanilla behaviour, and the entry-condition/clear-on-stop memory sets to declare. Two memory modules — trip target (`MemoryModuleType<GlobalPos>`) and cooldown (`MemoryModuleType<Long>`) — registered and saved through ordinary brain memory persistence, no schema of this mod's own (`contracts/data-contract.md`, `DATA-REQ-001..004`; `ARCH-DEC-005`). The restock hook that rolls the configured chance (default 50%) once per restock, not per offer (`CUSTOMER-REQ-002`; `DEC-009`; `CUSTOMER-DEC-001`) — first step: find where `Villager.restock()`/`shouldRestock()` runs and hook it narrowly, without touching the vanilla reset itself. The search through `VC-2`'s `ShopSearch` (`CUSTOMER-REQ-003`), the walk through `SetWalkTargetFromBlockMemory` with a 2-block arrival distance, a 2,400-tick timeout, and a 2,400-tick cooldown after a cancelled or timed-out trip, independent of the restock cycle (`CUSTOMER-REQ-004`, `007`; `CUSTOMER-DEC-002`). Cancel on panic, on leaving `WORK`, or on the target losing its shophood before arrival (`CUSTOMER-REQ-006`, `007`; `SHOP-REQ-006`). Arrival hands off to `VC-3`'s transaction loop, then clears the trip memory (`CUSTOMER-REQ-005`). At most one active trip per villager (`CUSTOMER-REQ-008`); no match found leaves the villager idle with no error and no retry before the next restock (`CUSTOMER-REQ-009`).

## Approach

First thing to verify: the exact `WORK` priority slot and the `MemoryModuleType` entry-condition/clear-on-stop sets to declare (`ARCH-DEC-002`'s own "to verify at the first ticket") — `javap -p -c` `Villager.registerBrainGoals`/`makeBrain`/`refreshBrain` and `VillagerGoalPackages.getWorkPackage` to read the existing priority-bucketed list vanilla builds, so the new behaviour's slot is chosen deliberately rather than guessed. Second: find where `Villager.restock()`/`shouldRestock()` is called from and hook the chance roll there narrowly (a mixin `@Inject` at the point restock completes, not a wrapped replacement of the method). Classes: `villager_customers.customer.ShoppingTripBehavior` (a `Behavior<Villager>`/`BehaviorControl<Villager>` implementing the state machine in `domains/customer.md` §3: `idle` → `walking` → arrival/`cancelled`), `villager_customers.customer.VillagerBrainMixin` (the `registerBrainGoals` injection; also the home of the restock hook, or a second narrow mixin if the restock call site is a different method), `villager_customers.customer.CustomerMemoryModules` (registers `villager_customers:shopping_trip_target` and `villager_customers:shopping_cooldown`, both saved/loaded exactly as vanilla's own `HOME`/`JOB_SITE`/`CANT_REACH_WALK_TARGET_SINCE`). Walk via the generic `SetWalkTargetFromBlockMemory.create(MemoryModuleType<GlobalPos>, float speedModifier, int closeEnoughDist, int tooFarDistance, int timeoutTicks)`, the same pattern `GoToPotentialJobSite`/`WorkAtPoi` use for job sites — reused against the trip-target memory module rather than reinvented.

## Acceptance criteria

- [ ] `ShoppingTripBehavior` is registered into `Activity.WORK`'s priority set via the mixin at `Villager.registerBrainGoals` `RETURN`, at a slot chosen and recorded here after reading vanilla's own `WORK` package (`CUSTOMER-REQ-001`).
- [ ] Memory modules `villager_customers:shopping_trip_target` (`GlobalPos`) and `villager_customers:shopping_cooldown` (`Long`) are registered, present only while the states `data-contract.md` `DATA-REQ-001`/`002` name, and round-trip a save/load through ordinary brain memory persistence (`DATA-REQ-001..004`).
- [ ] The restock hook rolls the configured chance (data constant, default 50%) exactly once per restock, never per offer (`CUSTOMER-REQ-002`; `CUSTOMER-DEC-001`).
- [ ] On a successful roll, `ShopSearch` (`VC-2`) is queried and, on a match, the shop's position is remembered as the trip target (`CUSTOMER-REQ-003`).
- [ ] The walk uses `SetWalkTargetFromBlockMemory` against the trip-target memory: 2-block arrival distance, 2,400-tick timeout (`CUSTOMER-REQ-004`).
- [ ] On arrival, the transaction loop (`VC-3`) is invoked, then the trip memory is cleared (`CUSTOMER-REQ-005`).
- [ ] The trip is cancelled and memory cleared on panic, on the villager's activity leaving `WORK`, and when the target loses its shophood before arrival (rechecked via `VC-2`'s live `Shop.isShop()`); a 2,400-tick cooldown starts before the next roll is permitted (`CUSTOMER-REQ-006`, `007`; `CUSTOMER-DEC-002`).
- [ ] At most one active trip memory exists per villager at any time (`CUSTOMER-REQ-008`); a roll that finds no matching offer or no matching shop leaves the villager idle with no error and no retry before the next restock (`CUSTOMER-REQ-009`).
- [ ] Game test: with a forced roll, a villager already in `WORK` next to a matching shop executes the trade within the 2,400-tick timeout.
- [ ] Game test: in a redstone-free world at night (villager not in `WORK`), no trip starts even with a forced roll.
- [ ] Game test: a shop removed mid-walk cancels the trip, clears the memory, and starts the cooldown, with no partial transaction (`UC-007`).
- [ ] Game test: the mixin coexists with at least one other mod that also mixins `Villager.registerBrainGoals` (`TEST-REQ-003`; `ARCH-FAIL-004` — `Brain.addActivity` is additive per activity, so this proves coexistence rather than assumes it).

## Constraints and prior findings

`04-architecture.md` `ARCH-DEC-002`: no Fabric event fits (`fabric-entity-events-v1`, `fabric-lifecycle-events-v1`, `fabric-events-interaction-v0` all checked exhaustively, research §C) — `Villager.registerBrainGoals(Brain<Villager>)` is private but is the narrowest target both `makeBrain` (spawn) and `refreshBrain` (profession change) funnel through. Research §B: 26.2 replaced `Schedule`/`ScheduleBuilder` with a compiled, non-data-driven `EnvironmentAttribute<Activity>` system (`EnvironmentAttributes.VILLAGER_ACTIVITY`); `Brain.addActivity(Activity, ImmutableList<Pair<Integer,BehaviorControl<? super E>>>, Set<Pair<MemoryModuleType<?>,MemoryStatus>>, Set<MemoryModuleType<?>>)` is the public wiring method vanilla itself uses. `CUSTOMER-DEC-001`: one roll per restock decides whether the villager searches at all; the search then considers every eligible offer — if this reading of the rulings is wrong, `CUSTOMER-REQ-002`/`003` split into a per-offer loop instead, a small rewrite. `CUSTOMER-DEC-002`: the cooldown is independent of the restock cycle specifically so a cancelled trip cannot retry on the very next restock against the same broken shop. `ARCH-FAIL-003`: an unloaded chunk mid-trip is not this mod's problem — vanilla does not tick unloaded entities, so the trip resumes or times out once loaded again, same as any vanilla walk-target behaviour. Blocked by `VC-2` (the shop search this behaviour queries) and `VC-3` (the transaction loop arrival hands off to) — this ticket is the hand-off point between both and cannot be proven end to end without them.
