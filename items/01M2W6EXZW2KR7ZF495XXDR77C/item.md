## Scope

How a villager decides to go shopping, finds a target, walks there, and every way that trip can end (`docs/spec/domains/customer.md`, `CUSTOMER-REQ-001..009`; `04-architecture.md` `ARCH-DEC-002`, `ARCH-DEC-005`; `decisions/DEC-009-chance-per-restock.md`). A mixin on `Villager.registerBrainGoals(Brain<Villager>)`, injected at `RETURN`, adding a `ShoppingTrip` behaviour as one candidate in `Activity.WORK`'s priority set via `Brain.addActivity(...)` (`CUSTOMER-REQ-001`) — first step: read vanilla's `WORK` activity package (`VillagerGoalPackages.getWorkPackage`) to pick a priority slot that does not collide with an existing vanilla behaviour, and the entry-condition/clear-on-stop memory sets to declare. Two memory modules — trip target (`MemoryModuleType<GlobalPos>`) and cooldown (`MemoryModuleType<Long>`) — registered and saved through ordinary brain memory persistence, no schema of this mod's own (`contracts/data-contract.md`, `DATA-REQ-001..004`; `ARCH-DEC-005`). The restock hook that rolls the configured chance (default 50%) once per restock, not per offer (`CUSTOMER-REQ-002`; `DEC-009`; `CUSTOMER-DEC-001`) — first step: find where `Villager.restock()`/`shouldRestock()` runs and hook it narrowly, without touching the vanilla reset itself. The search through `VC-2`'s `ShopSearch` (`CUSTOMER-REQ-003`), the walk through `SetWalkTargetFromBlockMemory` with a 2-block arrival distance, a 2,400-tick timeout, and a 2,400-tick cooldown after a cancelled or timed-out trip, independent of the restock cycle (`CUSTOMER-REQ-004`, `007`; `CUSTOMER-DEC-002`). Cancel on panic, on leaving `WORK`, or on the target losing its shophood before arrival (`CUSTOMER-REQ-006`, `007`; `SHOP-REQ-006`). Arrival hands off to `VC-3`'s transaction loop, then clears the trip memory (`CUSTOMER-REQ-005`). At most one active trip per villager (`CUSTOMER-REQ-008`); no match found leaves the villager idle with no error and no retry before the next restock (`CUSTOMER-REQ-009`).

## Approach

First thing to verify: the exact `WORK` priority slot and the `MemoryModuleType` entry-condition/clear-on-stop sets to declare (`ARCH-DEC-002`'s own "to verify at the first ticket") — `javap -p -c` `Villager.registerBrainGoals`/`makeBrain`/`refreshBrain` and `VillagerGoalPackages.getWorkPackage` to read the existing priority-bucketed list vanilla builds, so the new behaviour's slot is chosen deliberately rather than guessed. Second: find where `Villager.restock()`/`shouldRestock()` is called from and hook the chance roll there narrowly (a mixin `@Inject` at the point restock completes, not a wrapped replacement of the method). Classes: `villager_customers.customer.ShoppingTripBehavior` (a `Behavior<Villager>`/`BehaviorControl<Villager>` implementing the state machine in `domains/customer.md` §3: `idle` → `walking` → arrival/`cancelled`), `villager_customers.customer.VillagerBrainMixin` (the `registerBrainGoals` injection; also the home of the restock hook, or a second narrow mixin if the restock call site is a different method), `villager_customers.customer.CustomerMemoryModules` (registers `villager_customers:shopping_trip_target` and `villager_customers:shopping_cooldown`, both saved/loaded exactly as vanilla's own `HOME`/`JOB_SITE`/`CANT_REACH_WALK_TARGET_SINCE`). Walk via the generic `SetWalkTargetFromBlockMemory.create(MemoryModuleType<GlobalPos>, float speedModifier, int closeEnoughDist, int tooFarDistance, int timeoutTicks)`, the same pattern `GoToPotentialJobSite`/`WorkAtPoi` use for job sites — reused against the trip-target memory module rather than reinvented.

## Acceptance criteria

- [x] `ShoppingTripBehavior` is registered into `Activity.WORK`'s priority set via the mixin at `Villager.registerBrainGoals` `RETURN`, at a slot chosen and recorded here after reading vanilla's own `WORK` package (`CUSTOMER-REQ-001`).
- [x] Memory modules `villager_customers:shopping_trip_target` (`GlobalPos`) and `villager_customers:shopping_cooldown` (`Long`) are registered, present only while the states `data-contract.md` `DATA-REQ-001`/`002` name, and round-trip a save/load through ordinary brain memory persistence (`DATA-REQ-001..004`).
- [x] The restock hook rolls the configured chance (data constant, default 50%) exactly once per restock, never per offer (`CUSTOMER-REQ-002`; `CUSTOMER-DEC-001`).
- [x] On a successful roll, `ShopSearch` (`VC-2`) is queried and, on a match, the shop's position is remembered as the trip target (`CUSTOMER-REQ-003`).
- [x] (met with the same semantics: the behaviour sets `WALK_TARGET` from the trip-target memory itself, 2-block close-enough, the base `Behavior` duration as the 2,400-tick timeout; review 2026-09-19) The walk uses `SetWalkTargetFromBlockMemory` against the trip-target memory: 2-block arrival distance, 2,400-tick timeout (`CUSTOMER-REQ-004`).
- [x] On arrival, the transaction loop (`VC-3`) is invoked, then the trip memory is cleared (`CUSTOMER-REQ-005`).
- [x] The trip is cancelled and memory cleared on panic, on the villager's activity leaving `WORK`, and when the target loses its shophood before arrival (rechecked via `VC-2`'s live `Shop.isShop()`); a 2,400-tick cooldown starts before the next roll is permitted (`CUSTOMER-REQ-006`, `007`; `CUSTOMER-DEC-002`).
- [x] At most one active trip memory exists per villager at any time (`CUSTOMER-REQ-008`); a roll that finds no matching offer or no matching shop leaves the villager idle with no error and no retry before the next restock (`CUSTOMER-REQ-009`).
- [x] Game test: with a forced roll, a villager already in `WORK` next to a matching shop executes the trade within the 2,400-tick timeout.
- [x] Game test: in a redstone-free world at night (villager not in `WORK`), no trip starts even with a forced roll.
- [x] Game test: a shop removed mid-walk cancels the trip, clears the memory, and starts the cooldown, with no partial transaction (`UC-007`).
- [x] (proven by a second `Brain.addActivity` into WORK from the test and both behaviours read back through reflection) Game test: the mixin coexists with at least one other mod that also mixins `Villager.registerBrainGoals` (`TEST-REQ-003`; `ARCH-FAIL-004` — `Brain.addActivity` is additive per activity, so this proves coexistence rather than assumes it).

## Constraints and prior findings

`04-architecture.md` `ARCH-DEC-002`: no Fabric event fits (`fabric-entity-events-v1`, `fabric-lifecycle-events-v1`, `fabric-events-interaction-v0` all checked exhaustively, research §C) — `Villager.registerBrainGoals(Brain<Villager>)` is private but is the narrowest target both `makeBrain` (spawn) and `refreshBrain` (profession change) funnel through. Research §B: 26.2 replaced `Schedule`/`ScheduleBuilder` with a compiled, non-data-driven `EnvironmentAttribute<Activity>` system (`EnvironmentAttributes.VILLAGER_ACTIVITY`); `Brain.addActivity(Activity, ImmutableList<Pair<Integer,BehaviorControl<? super E>>>, Set<Pair<MemoryModuleType<?>,MemoryStatus>>, Set<MemoryModuleType<?>>)` is the public wiring method vanilla itself uses. `CUSTOMER-DEC-001`: one roll per restock decides whether the villager searches at all; the search then considers every eligible offer — if this reading of the rulings is wrong, `CUSTOMER-REQ-002`/`003` split into a per-offer loop instead, a small rewrite. `CUSTOMER-DEC-002`: the cooldown is independent of the restock cycle specifically so a cancelled trip cannot retry on the very next restock against the same broken shop. `ARCH-FAIL-003`: an unloaded chunk mid-trip is not this mod's problem — vanilla does not tick unloaded entities, so the trip resumes or times out once loaded again, same as any vanilla walk-target behaviour. Blocked by `VC-2` (the shop search this behaviour queries) and `VC-3` (the transaction loop arrival hands off to) — this ticket is the hand-off point between both and cannot be proven end to end without them.

## Findings

**`WORK` priority slot: 6.** `javap -p -c` against `VillagerGoalPackages.getWorkPackage` (bytecode traced pair by pair, not guessed) shows vanilla's own outer priorities as `{2, 3, 5, 5, 10, 10, 99}`: 2 the `JOB_SITE` walk (`SetWalkTargetFromBlockMemory`), 3 `GiveGiftToHero`, 5 the minimal-look pair and, separately, the composter/POI/harvest/bonemeal `RunOne` pool, 10 `ShowTradesToPlayer` and `SetLookAndInteract`, 99 `UpdateActivityFromSchedule`. 6 sits free between the two clusters. `registerBrainGoals` itself does not build these lists in 26.2 — it only sets the schedule attribute and calls `updateActivityFromSchedule`; the activity/behaviour lists are built once, per class, by the static `BRAIN_PROVIDER` lambda, and are already present on the `Brain` by the time `registerBrainGoals` runs (both `makeBrain` and `refreshBrain` call `BRAIN_PROVIDER.makeBrain(...)` first) — confirming `ARCH-DEC-002`'s injection point is safe.

**Restock injection point: `Villager.restock()`, `@At("RETURN")`.** The method is public, linear (reset every offer's uses, resend, stamp `lastRestockGameTime`, increment `numberOfRestocksToday`), with no early return to miss.

**Memory-status sets, and a real crash this ticket's own game tests caught.** `ShoppingTripBehavior`'s entry condition declares `SHOPPING_TRIP_TARGET → VALUE_PRESENT` (the functional gate) and, critically, `SHOPPING_COOLDOWN → REGISTERED`. `Brain.addActivity` (bytecode traced) auto-registers, into the villager's own fixed memory-slot map, every `MemoryModuleType` a newly added behaviour's `getRequiredMemories()` names (`Brain.registerMemory`, private) — this is the *only* way a brand-new `MemoryModuleType` becomes usable on a real `Villager` `Brain` at all, whose slot map is otherwise fixed to vanilla's own hard-coded list; registering the type in `BuiltInRegistries.MEMORY_MODULE_TYPE` (for its codec) does nothing for this. Without `SHOPPING_COOLDOWN` in the entry-condition map, `Brain.setMemory`/`getMemory` on it threw `IllegalStateException: Unregistered memory fetched: villager_customers:shopping_cooldown` — caught by two of this ticket's own game tests before the fix, not by inspection. `MemoryStatus.REGISTERED` (confirmed via `Brain.checkMemory`'s bytecode) only requires the slot to exist, never a value, so this costs nothing functionally. `WORK`'s own `memoriesToEraseWhenStopped` set in the mixin's `addActivity` call names only `SHOPPING_TRIP_TARGET`, not the cooldown, so a cooldown started by a cancellation survives an activity change.

**`CustomerHooks.onRestock` gates the whole mechanism on `Activity.WORK`, not only the walk.** `CUSTOMER-REQ-001` reads narrowly as "the behaviour runs in `WORK`"; the night game test (villager resting, forced roll) requires no trip memory at all afterward, not merely no walking. `onRestock` therefore returns immediately unless `brain.isActive(Activity.WORK)`, before touching the cooldown or trip-target memory at all — a restock during `REST` neither rolls nor remembers a target. Recorded here since the spec's own wording did not resolve it explicitly.

**Package placement: `CustomerRules` moved to `villager_customers.model` in review.** First landed in `villager_customers.customer` per this ticket's own "What to build" wording; `docs/spec/operations/testing.md` and `model`'s own package-info both describe "the chance roll" as belonging to the pure, `verifyPurePackage`-enforced package, so review resolved the mismatch by moving `CustomerRules` (and `CustomerRulesTest`) into `model` — no Minecraft/Fabric/Create import, so the move needed no code change to the class itself, only its package line, its callers' imports (`villager_customers.customer.CustomerHooks`, `ShoppingTripBehavior`), and the test's location. `verifyPurePackage` now actually covers it (it only scans `model`); confirmed green afterward. The test-only roll-source seam (`CustomerHooks.setRollSourceForTesting`/`resetRollSourceForTesting`) stays in `customer`, since it is not pure — `CustomerHooks` is the only caller that needs the game to exist at all.

**Game-test setup simplified from the ticket's suggestion.** No profession or job site is set on the test villagers: `WORK`'s own `ActivityData` carries an empty conditions `Set` (confirmed via `javap` on `ActivityData.create`'s two-arg overload, which is what vanilla's `getWorkPackage` list is wrapped in), so activating `WORK` needs neither — and giving a villager profession `FARMER` risks `AbstractVillager.getOffers()`'s lazy `updateTrades(ServerLevel)` populating real, randomised vanilla farmer trades ahead of the test's own exact-shape offer, a flakiness risk not worth taking for a behaviour that itself only depends on `SHOPPING_TRIP_TARGET`.

**"Shop removed mid-walk" spawns 8 blocks away, not 20.** `ShopSearchGameTest`'s own Javadoc documents that Fabric's game-test batches place structures roughly a dozen blocks apart, and a search at the production `ShopSearch.VILLAGE_REACH` (48) from a test that close to its neighbours risks crossing into one; 8 blocks is comfortably clear of the 2-block arrival distance to still prove a genuine mid-walk cancellation, while staying inside one test's own structure.

**Coexistence test route: reflection into `Brain`'s private `availableBehaviorsByPriority` field** (`Map<Integer, Map<Activity, Set<BehaviorControl<? super E>>>>`, confirmed by name via `javap -p`), read only from the game test, never from production code. A second, trivial `BehaviorControl<Villager>` is added to `WORK` via the villager's own real `brain.addActivity(...)` call from the test, alongside the real `ShoppingTripBehavior` the mixin already added at spawn; both are asserted present, proving `Brain.addActivity`'s additive semantics rather than assuming them (`ARCH-FAIL-004`, `TEST-REQ-003`).
